# 工作区文件记忆规范 v2.0

> 适用对象：个人在 DSH 中管理的三类工作区——开发项目、运维管理、知识学习。
> 载体：纯 Markdown 文件（`AGENTS.md` + `docs/`），进 git，零运行时依赖。
> 本规范配套技能：`project-memory-init`（自动生成 + 自检）。
> v2.0 相对 v1.2：新增运维/知识两类工作区与 `RUNBOOK.md` / `NOTES.md`；新增「边界与红线」节；触发器按类型分版；补齐拒绝写入清单、复验与归档、并发与快照操作步骤、跨机器同步。

---

## 0. 适用边界（先读）

这套体系解决的是：**同一工作区的不同会话之间，信息丢失、重复解释、旧结论污染**。
它**不承诺**提升任务成功率，也不替代代码、README 或工单系统。

三条边界：

1. 只写「对该工作区任何会话都恒真、且不能从代码/文件中直接推导」的内容；仓库概览、进度、临时状态一律去动态层。
2. 必须每次生效的规则放 `AGENTS.md`（每次会话自动注入）；自动记忆、向量检索、会话摘要只做补充，不做唯一真源。
3. 文件是唯一共享记忆：能进 git、能被其他工具读、能被人工审 diff。不要引入数据库、向量库、插件或联网服务。

## 1. 三类工作区与文件矩阵

| 文件 | 角色 | 变更频率 | dev | ops | knowledge | 长度预算 |
|---|---|---|---|---|---|---|
| `AGENTS.md` | 宪法/索引 | 极低 | ✅ | ✅ | ✅ | ≤ 60 行 |
| `docs/PROGRESS.md` | 工作日报 | 每次工作 | ✅ | ✅ | ✅ | ≤ 120 行，已完成 ≤ 30 条 |
| `docs/KNOWN-ISSUES.md` | 坑与故障 | 踩坑即记 | ✅ | ✅ | ✅ | ≤ 120 行，已修复 ≤ 20 条 |
| `docs/DECISIONS.md` | 决策与理由 | 定案即记 | ✅ | ✅ | ✅ | ≤ 300 行 |
| `docs/RUNBOOK.md` | 可重复操作步骤 | 低频 | 可选¹ | ✅ | — | ≤ 300 行 |
| `docs/NOTES.md` | 知识笔记与索引 | 按学习节奏 | — | — | ✅ | ≤ 300 行 |

¹ 开发项目若含部署/发布/服务器操作，追加 `RUNBOOK.md`，主类型仍为 `dev`。
旧项目已有 `AGENTS.md` 时只补缺，不改写已有保护节；历史文件不删除，停用就在指针里标「已停用」。

## 2. 五条原则

1. **文件优先**：对话易失，文件持久；值得跨会话记住的东西必须落盘。
2. **稳定层 / 动态层分离**：`AGENTS.md` 只放恒真事实；进度、坑、决策、操作步骤各归其位。
3. **准入判据**：只写「对该工作区任何会话都恒真 + 不能从代码/文档直接推导」的内容。两条缺一，不进稳定层。
4. **拒绝写入清单**【禁止】：
   - 密钥、令牌、密码、账号、私钥、cookie（只写获取位置）
   - 未验证的推断、无来源的结论、LLM 生成的仓库概览
   - 一次性状态、临时方案、当前分支/会话状态（→ PROGRESS）
   - 模糊要求（「代码写好一点」）、可从代码直接看出的目录清单
   - 大段原文抄录、聊天记录全文
5. **零依赖**：只依赖 Markdown 阅读器与 git；校验脚本只读、无网络、无安装。

## 3. AGENTS.md 规范

### 3.1 结构（类型差异由技能拼装）

```text
# <工作区名>
> 类型: <开发/运维/知识> · 建立: YYYY-MM-DD · 最后核对: YYYY-MM-DD
> <一句话说明>

<类型专属节>

## 工作约定
## 边界与红线
## 进度衔接（必须保留本节原文）
## 自维护触发器（必须保留本节原文）
## 记忆文件
```

类型专属节：

- **dev**：技术栈 / 常用命令 / 项目结构
- **ops**：管理对象 / 环境与访问 / 危险操作红线 / 常用操作
- **knowledge**：学习范围 / 知识约定 / 当前关注

「边界与红线」四行所有类型通用：不写秘密；不把推断当结论；复述后未经确认不自动开工；改记忆文件用编辑工具且并发先读。

「记忆文件」节只放指针，不摘抄内容：进度、已知坑、决策三行必写；有 RUNBOOK/NOTES 时各加一行。

### 3.2 写作守则

- 一条一行、祈使句、可执行；每条能回答「照着做了吗」。
- 目标 35～45 行，硬上限 60 行；每行都按会话轮次付 token。
- 措辞分档：**禁止** = 会造成泄漏/数据丢失/污染；**必须** = 有触发条件且可检验；**建议** = 可裁剪。全文「必须」条目控制在 10 条以内。
- 具体到命令/路径/字段，不写「注意维护好」。
- 不复制 README（README 给人，AGENTS.md 给 agent）。

### 3.3 反模式（禁止）

- 写当前进度、本周计划、最近改动（→ PROGRESS）
- 示例命令当成项目命令（初始化时只从模板复制，示例块禁止复制）
- 子目录与根 AGENTS.md 对同一主题写两份规则（软语义，会打架）
- 超过一屏的背景介绍；密钥明文；无来源的数字
- 为了更新而更新（见 §9.3 周报警线）

### 3.4 保护节

「进度衔接」「自维护触发器」两节含「（必须保留本节原文）」标记，生成后**逐字保留**，不得增删改；技能校验脚本会比对原文。
触发器按类型分版（dev / ops / knowledge），其原文见附录 A。

## 4. docs/PROGRESS.md

### 4.1 结构

```markdown
# PROGRESS — <工作区名>
> 最后更新: YYYY-MM-DD HH:mm

## 当前状态      ← 1~3 句：进行到哪、在做什么、卡在哪
## 已完成        ← [YYYY-MM-DD] 动词开头 + 关键文件/PR 路径；新条目放最上
## 下一步        ← [ ] 具体到「打开哪个文件、做什么」；禁止「继续完善」
## 已知问题      ← 未解决 bug、技术债、待定决策（可选）
```

### 4.2 更新纪律

- 完成任一可交付单元、计划变更、会话结束前（**哪怕任务夭折**）都要更新。
- 「当前状态」只写最新事实；被取代的旧状态移入「已完成」。
- 带日期；按时间倒序；附相对路径。
- 并行会话写前必须 `read` 最新版再改（读-改-写），否则后写覆盖先写。
- 「最后更新」距今 > 7 天且项目仍在动 → 收尾时提醒用户核对。

### 4.3 归档

「已完成」> 30 条 → 旧条目移入 `docs/archive/progress-<年份>.md`（移动，不删除）。

## 5. docs/KNOWN-ISSUES.md

### 5.1 结构

```markdown
# 已知坑 — <工作区名>
> 高频动态文件：踩坑即记，允许频繁变更。每条必须含 现象 / 原因 / 规避。

## 坑列表（新坑放最上）
- [YYYY-MM-DD] 现象: …；原因: …；规避: …

## 已修复
- [YYYY-MM-DD] <修复结论与关键改动>
```

### 5.2 纪律

- 踩坑解决或排障出结论时即记；三要素（现象/原因/规避）缺一不可。
- 「已修复」> 20 条 → 移入 `docs/archive/known-issues-<年份>.md`。
- 过时条目不得静默留着：复核后选「保留 / 归档 / 删除」之一。
- 运维场景中，事故与故障也可记这里；长流程放 RUNBOOK，结论与坑放这里。

## 6. docs/DECISIONS.md

### 6.1 结构（轻量 ADR）

```markdown
# 决策记录 — <工作区名>
> 低频稳定文件：记录「为什么这么做」。已定案条目不改写；被取代时新起条目并标注「取代 <日期> 决策」。

## 决策列表（新决策放最上）
- [YYYY-MM-DD] 一句话摘要（状态: 生效）

### [YYYY-MM-DD] <决策主题>
- 背景: 要解决什么问题
- 决策: 做了什么选择
- 备选: 考虑过什么、为什么否决
- 原因: 一句话核心理由
- 状态: 生效 / 已被 <日期> 决策取代
```

### 6.2 纪律

- 做出影响后续工作的选择时，定案即记；每个决策约 2 分钟。
- 历史不可篡改：不改旧条目；推翻时新增条目并标明取代关系。
- 「为什么」优先于「做了什么」；不写会议流水账。

## 7. docs/RUNBOOK.md（运维 / 可选）

### 7.1 结构

```markdown
# RUNBOOK — <工作区名>
## 管理对象        ← 对象 / 角色 / 入口（凭据只写位置）
## 日常操作        ← 每步可复制执行
## 故障排查        ← 按症状索引
## 备份与恢复
## 变更与回滚      ← 每次变更前写回滚方式
```

### 7.2 纪律

- 只写「怎么做」；「为什么」→ DECISIONS。坑与事故结论 → KNOWN-ISSUES。
- 危险步骤必须有：前置检查、确认点、回滚方式；未演练的命令不进生产。
- 步骤保持可复制；主机名/路径/端口写实际值，不写「相应目录」。
- 环境差异（生产/测试）单独标注；所有凭据只写获取位置。
- 对象超过 15 个时按系统拆分文件，RUNBOOK 保留索引。

## 8. docs/NOTES.md（知识学习）

### 8.1 结构

```markdown
# NOTES — <工作区名>
## 主题索引      ← 表格：主题 / 状态 / 最近更新 / 入口
## 笔记（新笔记放最上）
### [YYYY-MM-DD] <主题>
- 结论:
- 依据/来源:      ← URL / 文件 / 会话；区分事实 / 推断 / 观点
- 适用范围:
- 待验证:
```

### 8.2 纪律

- 每条结论必须有来源与日期；来源失效或结论过期时标注，不静默删除。
- 区分「事实 / 推断 / 观点」；不确定写「待验证」。
- 只写可复用结论，不抄原文、不堆链接；主题多时按领域拆文件，索引留在 NOTES。
- 学习会话的产出优先「讲清楚 + 可追溯」；不必每次强行落文件。

## 9. 维护闭环

### 9.1 触发器 → 写入位置

| 事件 | 更新 |
|---|---|
| 依赖/框架变化 | AGENTS.md「技术栈」 |
| 脚本命令变化 | AGENTS.md「常用命令」 |
| 核心目录重组 | AGENTS.md「项目结构」 |
| 管理对象/访问入口变化 | AGENTS.md「管理对象」「环境与访问」 |
| 运维步骤变化 | docs/RUNBOOK.md + AGENTS.md 触发器对应行 |
| 踩坑/故障结论 | docs/KNOWN-ISSUES.md |
| 架构/方案/取舍定案 | docs/DECISIONS.md |
| 形成知识结论 | docs/NOTES.md |
| 进度变化（每会话） | docs/PROGRESS.md |

### 9.2 收尾三件套 + 人工门禁

会话收尾按顺序问自己三句：

1. `PROGRESS.md` 更新了吗？（必须）
2. 本次踩坑/决策了吗？（是 → 对应文件）
3. 本次触发 AGENTS.md 触发器了吗？（是 → 收尾批量改一次）

人工门禁：用户收尾时问一句「PROGRESS.md 更新了吗？」；agent 汇报时必须显式说明更新了哪些记忆文件。

### 9.3 批量提交与周报警线

- 一次会话最多产生 **1 次** `AGENTS.md` 变更；触发多处时收尾统一改。
- 每自然周 `AGENTS.md` 变更 > 1 次 = 内容放错层：把最活跃的节降级到 `docs/`，并在 PROGRESS 记录这次降级。

### 9.4 快照陷阱【必须】

- 当前会话里的 `AGENTS.md` 是加载时快照；只有 `read`/`write`/`edit` 成功后才可能刷新。
- 修改记忆文件必须用 `read`/`write`/`edit` 工具，**禁止**用 bash `sed`/`cat >`/外部编辑器改完就当已生效。
- 若已在会话外修改：立即让 agent `read` 一遍，再继续工作。

### 9.5 并发写【必须】

- 同工作区并行多会话时，写前必须 `read` 最新内容，基于最新版修改（读-改-写）。
- 无法协调时约定「同一时刻只有一个会话负责记忆文件」。
- 冲突时保留双方事实，手工合并；禁止直接覆盖。

### 9.6 执行节制

- agent 开工复述进度后，未经用户确认不得自动开始执行「下一步」。
- 「下一步」是给用户看的选项，不是自动任务队列。

### 9.7 复验、归档、降级

- 动态层条目超过 30 天未复验 → 收尾时提示复核；处置必须三选一：保留 / 归档 / 删除，禁止「先放着」。
- 归档 = 移动到 `docs/archive/`，不删除。
- 文件超预算时：把最活跃的节降级到 `docs/`（指针留在 AGENTS.md），并记录到 PROGRESS。

### 9.8 安全

- 任何记忆文件都不写明文秘密；只写「在哪找」（`.env`、密码管理器条目名、CI secret 名）。
- 公开仓库尤其注意：记忆文件会进 git 历史；误提交后需轮换凭据，而不只是删文件。
- 涉及生产环境的操作记录，只写步骤与结果，不贴完整命令输出中的敏感值。

### 9.9 多工具协作

- 其他 agent 工具也读 `AGENTS.md`，但不会强制遵守「必须保留本节原文」等约定；对它们按「降档」对待。
- 默认不生成 `CLAUDE.md`；确实混用时再加一行指针，并意识到它只是文本。

## 10. 初始化、迁移与跨机器

### 10.1 新工作区

1. 用 `project-memory-init` 技能：说「初始化项目」或 `/project-memory-init`。
2. 技能侦察 → 判定类型 → 生成 → 自检 → 汇报待补项。
3. 用户补齐 `（待补充）`，`git init` + commit（是否执行先问）。
4. 在新会话中验证：开工应自动读 PROGRESS 并复述。

### 10.2 已有项目升级（v1.2 → v2.0）

1. 先 `read` 现有 `AGENTS.md` 与 docs，备份或确保已提交。
2. 只做增量：补「边界与红线」、把「触发器」升级为对应类型原文、补 RUNBOOK/NOTES（如需要）。
3. 不动已有的「进度衔接」；不删除任何历史文件。
4. 升级后跑校验脚本；变更写进 PROGRESS，理由写进 DECISIONS。

### 10.3 类型切换

- 工作区从 dev 变 ops（或反之）：改 AGENTS.md 顶部类型与专属节；旧专属节降级到 docs/ 并标「已停用」，不直接删。
- 学习目录转为项目：保留 NOTES（作为背景资料），新增 dev 节；不要把笔记内容搬进 AGENTS.md。

### 10.4 跨机器与多人

- 推荐：把工作区（含记忆文件）放进 git 私有仓库，作为跨机器同步通道；开工前 `pull`，收尾后 `commit + push`。
- 不同机器同时编辑 → 按 §9.5 读-改-写；合并时保留双方事实。
- 不想把记忆文件进项目仓库时：单独建一个 `memory` 仓库/目录同步；但必须保证路径稳定、可追溯。
- 用户级全局偏好放 `~/.dsh/AGENTS.md`（≤ 20 行），只放跨项目恒真的内容；项目内容不放全局。

## 11. 验收自检表

每次收尾或每周一次：

- [ ] PROGRESS「当前状态」是最新事实，「最后更新」已刷新
- [ ] 本次踩坑 → KNOWN-ISSUES 三要素齐全；本次决策 → DECISIONS 四字段齐全
- [ ] 本次触发触发器 → AGENTS.md 已在收尾批量更新（本周 ≤ 1 次）
- [ ] AGENTS.md ≤ 60 行；两个保护节原文未被改动
- [ ] 无明文密钥/令牌；无 `<...>` / `{{...}}` 模板残留
- [ ] 动态层无超过 30 天未复验的条目（有则保留/归档/删除）
- [ ] 并行会话写前已 read；会话外改过文件已 read 刷新
- [ ] 类型专属文件齐全：ops 有 RUNBOOK；knowledge 有 NOTES
- [ ] `（待补充）` 数量在减少；没有假装完整
- [ ] 收尾汇报中明确说明更新了哪些记忆文件

校验命令：

```bash
node scripts/verify-memory.mjs <工作区根目录>
```

## 13. 依据摘要（结论 + 强度）

- 【强，负面】仓库级上下文文件总体不提升任务成功率、有额外成本；因此禁止「仓库概览」类内容，只写不可推导的恒真事实。
- 【强】同一项目的多会话/多工具共享记忆，纯 Markdown + git 是成本最低、最可审计的载体；自动记忆只能做补充层。
- 【中】动态层与稳定层分离、触发器表、收尾批量提交，能同时抑制「忘了更新」与「过度更新」。
- 【中】快照陷阱与压缩风险是 DSH 机制事实（源码/文档可核），因此记忆文件必须落盘、外部改动后必须 read。
